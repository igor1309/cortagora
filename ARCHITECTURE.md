# Repository Architecture

Этот документ фиксирует правила организации репозитория cortagora.

## 1. Layers

Репозиторий содержит несколько слоёв, каждый со своей семантикой:

- **works/** — конкретные проекты/произведения (единица ответственности)
- **world/** — глобальный world-material (worldbuilding layer; не канон)
- **research/** — надпроектный reference (исследования, обзоры, выжимки, инструменты)
- **framework/** — набор рабочих рамок и инструментов мышления:
  - framework/domains/, framework/protocols/, framework/modalities/, framework/personas/, framework/writing/
- **tools/** — утилиты и эксперименты
- **semi-RAG/** — “workshop”: временные тикеты/сборки/эксперименты retrieval
- **_inbox/** — входящее (до сортировки)
- **logs/** — журналирование

## 2. Work and scope

Scope начинается там, где присутствует `Work.md`.

Scope может быть:
- проектным (`works/<work>/Work.md`)
- сезонным (`works/<work>/s01/Work.md`)
- любым вложенным уровнем при необходимости

Каждый scope может иметь собственные (опциональные) папки:
- `project/` — ядро проекта (логлайн, название, манифест, журналы, ключевые документы), если папка используется
- `world/` — world-material этого scope (правила, нормы, институциональная логика; не канон)
- `canon/` — зафиксированные, необратимые факты и решения (минимальный слой), если нужен
- `characters/` — текущие рабочие версии персонажей, используемые при написании сцен, если папка используется
- `research/` — reference-материалы этого scope
- `sandbox/` (или `_ideas/`) — идеи/наброски/альтернативы этого scope
- `story/` / `episodes/` — сцены, синопсисы, эпизоды, версии текста
- `mechanics/`, `process/` — по необходимости (если в work принято так организовывать материал)

## 3. Presence-based

Наличие папки означает наличие данных на уровне scope.
Отсутствие папки означает отсутствие данных на этом уровне.

Никаких обязательных “пустых” папок.

## 4. Nearest wins

Контекст собирается снизу вверх:
1) текущий scope
2) родительский scope
3) корневой уровень репозитория

При конфликте побеждает ближайший (nearest wins).

Пример:
`works/deceptor/s01/world/` переопределяет `works/deceptor/world/`,
который переопределяет корневой `world/`.

То же верно для `canon/`, `characters/`, `research/`, `sandbox/` и любых co-located underscore-папок.

## 5. World vs canon

`world/` — это **world-material**: описание мира, атмосферы, институциональной логики и гипотез.
Это не обязательно консистентный “канон”.

`canon/` — это **явная фиксация** утверждённых фактов и решений, которые нельзя “тихо” переписать,
не ломая уже написанные сцены/структуру.

Правило: ничего из `research/` или `sandbox/` не становится каноном автоматически.

Размещение материалов:
- новые проектные материалы — в `works/<work>/...`
- корневой `world/` — глобальный world-material и легаси-материалы, исторически жившие вне `works/`

## 6. Co-located WIP (underscore folders)

Для черновиков и материалов в процессе используйте co-located underscore-папки рядом с контекстом:

- `_ideas/` — гипотезы и альтернативы
- `_research/` — источники и выжимки
- `_archive/` — устаревшие версии, которые нужно сохранить
- `_inspo/` — вдохновение и клиппинги (опционально)

Эти папки могут существовать на любом уровне scope (root / work / season) и появляются только при необходимости.

## 7. Naming (soft)

Жёсткий style guide не вводится, но для новых директорий рекомендуется:
- `lowercase` и `kebab-case` для папок и “узловых” файлов навигации
- внутри проектов допускаются русские имена файлов (исторически накопленные и новые)

## 8. Framework folders

`framework/*` — надпроектный слой и может использоваться любым work.

- `framework/domains/` — предметные области, методики и базовые рамки (reference + мыслительные схемы)
- `framework/protocols/` — протоколы взаимодействия и рабочие стандарты
- `framework/modalities/` — режимы работы/мышления
- `framework/personas/` — персональные профили и стили
- `framework/writing/` — методички по нарративу

## 9. Git policy

Git используется как:
- хранилище
- история изменений

Точка истины: `trunk`.
Сабмодули и сабтри не требуются.
Изменения структуры выполняются малыми шагами, чтобы не ломать навигацию.
